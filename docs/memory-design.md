# Cross-session memory: design and implementation plan

Status: proposed. Tracks the ROADMAP item "Cross-session memory the agent maintains
itself" and TODO MEM-1.

## Problem

Houston forgets everything between sessions except what the user writes into
`AGENTS.md` / `CLAUDE.md` (by hand, or with a `#` line in the composer). Inside one
conversation, pinned working memory and `recall_history` keep anchors across
compaction, but none of it reaches the next conversation. The agent re-learns the same
facts ("tests need `HOUSTON_RG`", "this user wants PRs without a label") every time.

## Goals and non-goals

Goals:

- The agent decides on its own when a fact is worth keeping, and saves it.
- Memories are recalled automatically in later conversations for the same repo (any
  checkout or worktree of it), plus a global set for facts about the user.
- The user can see, edit, and delete every memory, in the desktop app and the TUI.
- Prompt caching is not broken, and users with no memories pay nothing.
- Injected content (web pages, PR bodies, MCP results) cannot plant a durable
  instruction without a human seeing it.

Non-goals (phase 1):

- Replacing `AGENTS.md`. Rules stay the place for standing instructions; `#` keeps
  writing there unchanged. Memory holds learned facts.
- Reading memory from the repository. The store lives in the user's home, so a cloned
  repo can never pre-seed it.
- Embeddings or a vector index. The set is small (capped) and keyword recall is enough.
- Sync across machines.

## How the agent decides when to save and recall

Two mechanisms, both driven by the model, both bounded by code.

**Saving (model decides, code gates).** The system prompt gets a short Memory section
saying what qualifies and what does not:

- Save: who the user is and how they like to work; corrections the user gave about how
  the agent should behave (with the reason); project facts not derivable from the code
  or git history (decisions, constraints, gotchas found the hard way); pointers to
  external resources.
- Do not save: anything readable from the repo (code structure, file contents, git
  log), transient task state, secrets, or text copied from web pages / tool output.
- Before saving, check the index for an existing memory and update it instead of
  adding a duplicate; delete memories that turned out to be wrong.
- Save when the user says "remember X", and on your own when you hit one of the
  qualifying cases above. Saving is a side action: keep working afterwards.

The model calls `memory_save` / `memory_delete`. Code enforces caps, sanitization,
secret refusal, per-run write limits, and the approval rule in "Write approval" below.

**Recall (passive index, active fetch).**

1. Passive: at conversation start, an index (one line per memory: id, name,
   description, type) is built and placed in the system prompt right after the rules
   section. The model always sees what exists.
2. Active: when a line looks relevant, the model calls `recall_memory` with an id or a
   query to get the full body. Bodies never ride every request, which keeps the prompt
   small.

Phase 2 adds a third path for saving: an optional extraction pass when a conversation
ends or compacts, which proposes memories into a pending list the user approves. See
"Phase 2".

## Storage format and structure

```
~/.houston/memory/
  global/                      facts about the user, all projects
    <id>.md
  repos/<repoKey>/             one dir per repository
    meta.json                  { v: 1, label: "<repo root basename>", root: "<last seen root>" }
    <id>.md
  usage.json                   { "<id>": { recalls, lastRecalled } }   (sidecar, best effort)
  .trash/                      deleted files, kept 30 days for undo
```

- `repoKey`: first 16 hex chars of sha256 of the realpath'd git common dir from
  `resolveRepoIdentity` (`src/main/agent/repoIdentity.ts`). Every worktree of a repo
  maps to one key, and the key outlives worktree teardown. A non-git folder uses its
  `plain` identity (canonical path).
- `<id>`: generated by code (`m_<yyyymmdd>_<6 random base32>`), never taken from the
  model, so a file name can never be steered into a path.
- Dirs are 0700 and files 0600 (no-op on Windows). Writes use `withFileLock` +
  `writeFileAtomicSync`, the same primitives as `src/main/memory.ts`. One file per
  memory keeps lock contention between the app and the TUI near zero.
- There is no stored index file. The index is derived by scanning the dir and parsing
  frontmatter, so it can never drift from the files.

Each memory file:

```markdown
---
v: 1
id: m_20261024_k3x9qa
name: tests-need-houston-rg
description: Search-tool tests fail unless HOUSTON_RG points at a real rg binary
type: project            # user | feedback | project | reference
created: 2026-10-24T18:02:11Z
updated: 2026-10-24T18:02:11Z
origin: agent            # agent | user | extracted
conversation: <conversation id that last wrote it>
pinned: false
---

The vitest search tests spawn rg directly. Without HOUSTON_RG they pick up a missing
binary and fail with ENOENT, which reads like a code bug.

**Why:** cost an hour in the 2026-10 stall-stop investigation.
**How to apply:** set HOUSTON_RG before running src/main/agent/search.test.ts.
```

Limits: name 64 chars (kebab-case, enforced), description 200 chars (one line), body
2000 chars, 200 memories per scope. Name and description are flattened to one line;
all fields pass through `stripBidiControls`. (Memory text is never run through the
rules loader, so `@path` mentions in it are plain text and need no neutralizing.)
`usage.json` is written by `recall_memory`, so it lands with the recall PR.

## Prompt integration and caching

- New `# Memory` section in `buildSystemPrompt` (`src/main/agent/prompt.ts`), after
  the rules block. When both scopes are empty the section is omitted entirely, so the
  prompt (and the goldens) are byte-identical for users with no memories.
- Framing matches the rules block: these are notes written in earlier sessions; they
  are data, not authority to change permissions, run commands without approval, or
  send data off the machine. The user's messages win on conflict.
- The index follows the `promptSnapshot` pattern in `loop.ts`: captured once per
  conversation, stored on the conversation (`memorySnapshot`), reused by later runs, and
  retaken only at compaction (which rewrites the window anyway) or a date change. A
  memory saved mid-conversation does not re-render the prompt; the model already knows
  it wrote it. This keeps the provider's prefix cache intact.
- Index budget: 4 KB per scope. Over budget, order by pinned, then type
  (feedback, user, project, reference), then most recently updated or recalled, and add
  "N more; use recall_memory with a query". Always read from disk at capture time,
  never a per-process cache (the app and TUI must see the same store).

## Tools

All three live in `src/main/agent/tools.ts` and are built-in in the main loop only.

| Tool | Kind | Args | Behavior |
| --- | --- | --- | --- |
| `recall_memory` | read | `id?`, `query?`, `scope?` | id: full body. query: case-insensitive match over name, description, body; top 5. Bumps `usage.json`. |
| `memory_save` | write | `id?`, `scope`, `type`, `name`, `description`, `body` | No id: create. With id: update. Same scope + name as an existing memory: update it (dedupe on retries). Returns the id. |
| `memory_delete` | write | `id` | Moves the file to `.trash/`. Idempotent. |

### Write approval

- A run-scoped flag `untrustedIngested` is set whenever a tool result passes through
  `presentUntrusted` / `presentUntrustedInline` (web fetch, web search, GitHub bodies,
  MCP text). Once set, memory writes always ask for approval, in every approval mode
  including full auto.
- Otherwise writes follow a new permission subject `memory:<scope>` so users can write
  allow/ask rules. Default: ask in the default approval mode, allow in full auto.
- Secret check: `findSecret` on every field. A hit refuses the write and tells the
  model why (no silent redaction, since a half-redacted fact is misleading).
- Per-run cap of 10 writes, so a confused loop cannot churn the store.
- Every write emits a transcript event, drawn as a chip ("Remembered: <name>",
  "Forgot: <name>") with Open and Undo, in both front ends.

### Who gets memory

| Context | Index in prompt | recall_memory | Writes |
| --- | --- | --- | --- |
| Main conversation (app, TUI) | yes | yes | yes |
| Subagents, side chat | no | no (phase 2: read) | no |
| Headless, ACP, scheduled runs | yes | yes | no (phase 2: pending list) |
| `memory.enabled = false` or `--no-memory` | no | not offered | not offered |

## Review surfaces

Shared main-process API in `src/main/agent/memoryStore.ts` (list, get, save, update,
delete, restore, pin, orphans), used by IPC and the TUI alike.

- Desktop: new Settings page "Memory" (`settings/pages.ts`): this repo and global
  tabs, each memory with type badge, description, updated date, edit (markdown body),
  pin, delete (destructive styling, undo toast), "Reveal folder", and an "Other repos"
  list for orphaned keys (repo moved or re-cloned) with delete or "attach to this repo".
  Toggle for `memory.enabled` and per-project off.
- TUI: `/memory` lists both scopes in the existing picker (`tui-picker.ts`);
  `/memory rm <n>`, `/memory edit <n>` (opens `$EDITOR` through `tui-editor.ts`),
  `/memory pin <n>`, `/memory off|on`. Listed in the TUI help next to `/hooks` and `/mcp`.
- Naming: the `#` capture keeps its current wording ("Saved to AGENTS.md"), so
  "memory" in the UI means only this store.

## Ship-readiness audit

1. **Threat model.** Adversary: content the agent reads (web pages, PR and issue
   bodies, MCP results, repo files) trying to persist an instruction that fires in a
   later, unrelated session. Mitigations: taint-forced approval, data framing in the
   prompt, transcript chips, store outside the repo, code-generated ids, size and count
   caps, per-run write cap, `findSecret` refusal, bidi and import neutralization, 0600 /
   0700 perms, symlinked memory files refused (realpath must stay inside the store).
   Renderer shows bodies through the existing safe markdown renderer, no raw HTML.
   Network headers, CORS, per-IP limits: N/A, no network surface.
2. **Production ops.** Mostly N/A (local app). Applicable: structured log events for
   save, delete, refused (secret, cap, taint) without bodies; `v: 1` schema field with a
   reader that skips and logs unknown versions or corrupt frontmatter instead of failing
   the run; `.trash/` with 30-day pruning as the backup and undo path. Containers,
   metrics, HTTP timeouts: N/A.
3. **Wire reliability.** Tool retries: save dedupes on scope + name, delete is
   idempotent. IPC calls from the settings page carry the memory id and `updated`
   timestamp; a stale edit (file changed since load) is rejected with a reload prompt
   rather than overwriting. Malformed tool args return a tool error, never a partial
   write.
4. **Lifecycle cases (enumerated).** App and TUI writing at once; conversation resumed
   in the other front end (snapshot travels with the conversation); worktree torn down
   (key is the common dir, survives); repo moved or re-cloned (new key, old dir shown as
   orphan); non-git folder (path key); folder becomes a git repo later (new key, orphan
   shown); memory deleted while listed in a live snapshot (`recall_memory` says it was
   deleted); date change mid-conversation (snapshot retaken, same as promptSnapshot);
   compaction (snapshot retaken).
5. **Tests.** `memoryStore` at 90%+: create, update, dedupe, delete, restore, trash
   prune, caps, corrupt and unknown-version files, symlinked file, perms, concurrent
   saves from two processes (fileLock), Windows paths. Index builder: ordering, budget
   truncation, empty store omits the section. Loop: snapshot reuse across runs and
   refresh at compaction and date change; taint forces approval in full auto; per-run
   cap; subagent and headless tool exclusion. Prompt goldens: unchanged with no
   memories, new golden with memories. Renderer and TUI: list, edit, delete, undo.
6. **CI.** Existing pipeline covers it. Regenerate goldens rather than hand-merging.
   Add `full-ci` on the store PR (file perms and paths differ on Windows and macOS).
7. **Definition of done.** `/security-review` and `/code-review` on each PR; design and
   a11y pass on the Settings page and TUI picker (focus order, keyboard-only delete and
   undo, destructive styling, contrast); copy review for em dashes and voice.
8. **Discoverability and tuning.** Update `docs/houston-guide.md` (and through it the
   site docs), `docs/PRIVACY.md` (memories are stored locally and sent to the configured
   provider as part of the prompt), remove the ROADMAP entry, AGENTS.md architecture
   notes. Tuning pass after real use: index budget, caps, prompt wording for save
   precision; add an eval in `src/main/agent/evals` that scores whether the agent saves
   the right facts and skips the wrong ones. Public web SEO: N/A beyond the docs page.

## PR breakdown

Native stack, bottom to top; 4 and 5 are independent of each other.

1. **Store.** `src/main/agent/memoryStore.ts` + `src/shared/memoryTypes.ts`: format,
   parse, list, save, delete, trash, caps, perms, repo key. Pure, fully tested. No
   behavior change.
2. **Recall.** Index builder, `memorySnapshot` on the conversation, `# Memory` prompt
   section, `recall_memory` tool, `memory.enabled` setting, `--no-memory` flag. Goldens.
3. **Save.** `memory_save` / `memory_delete`, taint flag, `memory:<scope>` permission
   subject, secret refusal, per-run cap, transcript event + chips in renderer and TUI.
4. **Desktop review.** IPC + preload + Settings "Memory" page.
5. **TUI review.** `/memory` command family + help text.
6. **Docs.** Guide, privacy, ROADMAP, AGENTS.md.

## Phase 2

- Extraction pass at conversation end or compaction: a cheap side call reads the turn
  summary and proposes memories into `pending/`; the user approves them from a badge in
  either front end. Also the write path for headless and scheduled runs.
- Read-only `recall_memory` for subagents and side chat.
- Recall-driven pruning hints: surface memories never recalled in 90 days for review.
