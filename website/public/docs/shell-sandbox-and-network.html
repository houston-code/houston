Shell sandbox and network

Shell commands run under the host OS sandbox where one exists, confined to the project directory: writes outside the project are blocked, and network access is off by default.

  • macOS: Seatbelt (sandbox-exec).
  • Linux: bubblewrap (an unprivileged user namespace), when available.
  • Windows: no broadly-available equivalent, so shell commands run unconfined; Houston reports them as not sandboxed and never silently auto-approves one.

The structured file tools stay confined to the project on every platform. Network from run_shell is gated, not permanently off, and it is no longer implied by full auto: the sandbox can read your whole filesystem, so blanket outbound access plus full auto would be a one-command read-and-exfiltrate. Shell reaches the network only after a conscious per-run grant, either the one-time shell-network consent (full auto) or "Allow for run" on a shell command (ask / auto-edit). Plain "Allow" and "Always allow" run that one command offline, and until the run has the grant, each shell approval prompt says so. A command that needs the network (cloning, installing dependencies, gh, curl) is not impossible, it just needs that grant; declining runs the command offline instead of blocking it. A headless run (-p) has no prompt to grant it from, so the grant is a flag: --allow-shell-network lets shell commands reach the network for that run under any policy, and is not remembered for the next one. Without it, shell runs offline, except under --full-auto, where --on-approval allow (its default) also answers the shell-network consent. --on-approval allow alone never grants it under ask or auto-edit, since it approves each command the way plain "Allow" does. Offline, npm, pip, and cargo skip their usual retries, so an install that needs the network fails in about a second instead of a minute or more. Package-manager caches (npm, pip, yarn) are auto-redirected to a writable temp dir, so dependency installs need no cache workaround once network is on. On macOS, Python's bytecode cache goes there too, since the system python3 keeps it under ~/Library/Caches, which the sandbox can't write. Additional folders (Settings) can be added to the file tools' allowed roots and the shell sandbox to work across more than one repo.

Finding your toolchain. An app opened from the Dock doesn't read your shell startup files, so Houston adds the usual places runtimes live to the shell's PATH: Homebrew, nvm's default Node, fnm, Volta, mise, asdf, pyenv, rbenv, and the per-user bin dirs of Rust, Go, Bun, and Deno. A sandboxed command may stop the processes it started (build tools do this with their workers), but nothing outside its own sandbox.

When a runtime is missing. If a command fails because Node.js, Python, Go, Rust, Deno, or Bun isn't installed, the transcript says so and offers Install, which runs the install command (for example brew install node) in a new tab of the built-in terminal, outside the sandbox, so you can watch it and answer any prompt; there's also a link to the official download page. The agent is told not to attempt system installs itself and to wait for you rather than write code it can't run. The terminal clients print the same install command.

Egress allowlist. Granted shell network is not unrestricted: on macOS and Linux it is routed through a local proxy Houston controls, and the OS sandbox blocks any direct connection, so the proxy is the only road out. The proxy allows a destination only if its domain is on the egress allowlist: a built-in set of development infrastructure (package registries such as npm, PyPI, crates.io, RubyGems, Maven, Go; VCS hosts such as GitHub, GitLab, Bitbucket) plus any domains added in Settings under Sandbox egress. Each entry also covers its subdomains, a deny list wins over every allow, and edits apply immediately, mid run. A refused destination fails with an EGRESS_BLOCKED message naming the domain: that is policy, not an outage. Only HTTP(S) flows through the proxy, so other protocols (for example SSH) are blocked under the allowlist; use HTTPS remotes inside the sandbox, or switch the egress mode to "All domains" (Settings) to restore unrestricted granted network. On Windows, where no OS sandbox exists, the allowlist cannot be enforced. One Linux note: each command runs in its own network namespace whenever shell network isn't granted, and also under the allowlist, so a dev server started inside the sandbox is reachable only from that same command: not from the Preview panel, view_localhost, or later commands. Granting shell network with "All domains" restores the shared network there. The agent is told this on Linux and checks web apps with requests from the command that starts the server.

Secret redaction. Tool results, the transcript, and logs are scrubbed before the model or the UI sees them: well-known token formats and this install's stored secrets become [redacted:…]. A NAME=value line whose name marks it as a secret (SESSION_SECRET, ADMIN_PASSWORD, GITHUB_TOKEN, STRIPE_API_KEY, and the like), as cat .env, env, or grep prints it, keeps its name but shows the value as [redacted:env-secret]. The agent therefore refers to such a value by variable and file rather than repeating it, and a file write that would put a [redacted:…] placeholder where a value goes is refused, so writing back a file it read cannot replace the real secret with the placeholder.

Credential masking on egress. Houston's own network tools refuse to send a credential: before a web_fetch or web_search leaves the machine, its URL or query is scanned for a well-known token format or one of this install's stored secret values, and the call is refused if one is present. This is the outbound counterpart to the tool-result redactor (which scrubs secrets on the way back in), so a prompt-injected agent cannot exfiltrate a key by pasting it into a request. Note this covers Houston-mediated egress; a raw curl inside run_shell is bounded by the shell-network consent above, not by masking.

Untrusted content. A fetched page is written by whoever runs the site, an issue comment by whoever posted it, and an MCP result by whoever wrote what the server relays. So Houston treats the text these tools return as data rather than instructions, and it does not rely on the agent simply choosing to see it that way. The tools covered are web_fetch, web_search, the GitHub tools that read issue and pull request text (gh_issue_view, gh_issue_list, gh_pr_view, gh_pr_list), the GitHub tools that read CI (gh_run_view, gh_run_list, gh_pr_checks), and MCP tool results and resources. A pull request from a fork runs the fork's own workflow files, so its author writes the job and step names and everything its steps print to the log:

  • Fencing. That text is wrapped in an <untrusted-content-NONCE> fence with a fresh random nonce per call, and the system prompt tells the agent that anything inside it is attacker-controlled. The nonce is what makes the fence hold: with a fixed tag, the text could close the fence itself and carry on as if it were trusted. Fields GitHub guarantees (an issue's number, state, author, and URL, or a CI run's id, outcome, and URL) stay outside the fence so the agent can rely on them, while titles, bodies, labels, branch names, diffs, workflow, job, step, and check names, and CI logs go inside. Each comment gets its own fence with its author shown outside it, so one comment cannot pass itself off as a maintainer's reply. The GitHub tools that write (opening, commenting, reviewing, merging, checking out, closing, reopening) report the outcome in a line Houston writes, plus the new item's URL, and fence everything gh printed, because its messages quote titles and branch names.
  • Isolation. Content is scored for injection signals: text telling the reader to ignore prior instructions, a new persona, an instruction to send data to a URL, references to key material, text telling the reader to call Houston's own tools, characters hidden from a human reader. A web page or MCP result that looks like an attempt is not inlined at all. Instead a separate model call with no tools and no conversation history reads it and reports what it says, and only that report reaches the agent. The isolation is structural: there is nothing for the content to act through, and no earlier instructions to talk it out of. If that call fails, the content is withheld rather than passed through.
  • Warning. GitHub text and web search results that look like an attempt stay inline and fenced, with a warning naming the signals. The agent needs an issue's exact repro steps or a pull request's exact diff to do its job, and a summary would not do. Search results are short snippets, and any page the agent then opens goes through web_fetch and its isolation. Diffs and CI logs are fenced but not scored, because code and build output routinely contain the phrases the scoring looks for.
  • Cost. Ordinary content is unaffected and arrives verbatim, so documentation and code samples stay byte-exact. Only flagged content pays for the extra call. The score is deliberately loose, because a false positive costs one model call and some fidelity rather than a failed call.

Bidirectional text controls, which can make text render in a different order than it reads, are stripped from all fenced content. This is defense in depth behind the approval gate (you still approve network and MCP calls), not a replacement for it: the classifier is a heuristic, and anyone who knows it is there can word around it.
