Clients (where Houston runs)

  • Desktop app. The full GUI: chat sidebar, diffs, a right-hand dock with the live Preview and a Tasks list of background commands (stop them, read their output, see which port each holds), settings.
  • Interactive terminal (houston -i). A stay-resident REPL in the terminal. --continue reopens this folder's most recent chat at launch, --resume <id> a specific one. Conversation streams live, approvals and questions are answered inline, and slash commands switch settings mid-session. See "The terminal composer" below for how to type, paste, and edit a message.
  • Headless (houston -p "<prompt>"). Runs one prompt and writes the result to stdout, each model round's text once that round has finished, then exits. Read-only by default; add --full-auto to let it edit and run commands, --json for machine-readable events. Good for scripts and CI. With no human to answer approval prompts, --on-approval <allow|deny|fail> decides what a gated tool call gets: denied by default (allowed under --full-auto), with fail also exiting non-zero so a script can tell the run hit a permission wall. Nobody can answer a question either, so a headless run doesn't offer the agent ask_user: it is told no user is available, makes the call itself, and states its assumptions in the final answer. Approving a shell command with --on-approval allow is plain "Allow", so it runs without network; pass --allow-shell-network to let shell commands reach the network for the run (see "Shell sandbox and network").
    • Prompt from stdin. -p - reads the prompt from stdin, and so does a -p with no value when input is piped in (cat task.md | houston -p --json). The standalone CLI also reads a piped prompt with no -p at all.
    • Per-run settings. These apply to the one run and never change your saved settings: --effort <off|low|medium|high|xhigh> sets the reasoning effort; --max-turns <n> caps the model steps (a hard cap that never auto-extends); --max-cost <usd> tells the agent to wrap up once the run's estimated cost reaches that amount (a soft ceiling: the step in flight still finishes); --verify <command> runs that command when the agent stops after editing files and sends a failure back for a bounded fix-up pass (it needs a policy that can edit, such as --full-auto). A bad value exits 2 before anything runs.
    • --json result line. After one JSON line per agent event, the last line is a summary: {"type":"result", "status", "stopReason", "limitReason"?, "turns", "costUsd", "inputTokens", "outputTokens", "durationMs", "finalText", "receipt"?}. status is success, limit, stalled, approval_denied, or error; finalText is the agent's closing answer (the text after its last tool call); receipt is Houston's record of what the run actually ran (see "What actually ran"), present when it ran checks or changed files.
    • Exit codes. 0: the agent finished on its own. 1: an error or aborted run, a stalled agent, or a call refused under --on-approval fail. 2: a usage error (a bad flag value, or an empty prompt on stdin); nothing ran. 3: the run hit a budget before finishing (its step cap or the model's output limit).
  • Standalone CLI. The same -p and -i clients as a single self-contained Node script, with no desktop app and no browser engine. Runs on headless Linux servers; API keys come from environment variables.

All clients share one agent core, so tools, permissions, and skills behave the same across them. Some surfaces are desktop-only (the preview panel, spawning separate sidebar sessions, viewing localhost screenshots).
